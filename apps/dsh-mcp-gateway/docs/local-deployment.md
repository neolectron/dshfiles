## Why workspace approval is required

Yield currently lives in the Incentive ChatGPT workspace. The new tunnel is scoped to the owner's personal Platform organization **without an Incentive workspace grant**. It was deliberately kept separate from the existing read-only Discord tunnel.

Binding it to Incentive may make the transport reachable to other authorized workspace members. V1's injected gateway key represents the permitted tunnel population; it is not individual-user authentication. A personally installed plugin is not sufficient evidence that every transport caller is individually isolated.

The user has been asked to choose:

- Keep the prepared connection private and do not activate Yield; or
- Explicitly allow Incentive workspace access, retain personal-only plugin installation (no workspace publication), then test genuine Yield.

No workspace grant, existing-tunnel edit, anonymous MCP access or authentication bypass was applied after the denial. On continuation, inspect the pending answer first. If approved, update only this dedicated tunnel through the supported Platform UI, verify the plugin was not already created during the failed attempt, and retry the existing connector flow. First ask genuine Yield to call only `dsh_health`, then compare the returned project alias with tunnel dispatch/delivery evidence. Do not claim cloud success merely because polling is healthy.

## Operator commands

From the package root, the [verification client](../scripts/verify-local.mjs) defaults to health only:

```sh
node scripts/verify-local.mjs
node scripts/verify-local.mjs --confirm-create --project dshfiles
node scripts/verify-local.mjs --read-probe-task <existing-probe-task-id>
systemctl --user status dsh-mcp-gateway.service dsh-mcp-tunnel.service
curl --fail http://127.0.0.1:8791/readyz
```

Use `--credential-file /absolute/private/gateway.env`, never plaintext credentials as arguments. Node22 pre-scans its reserved `--env-file` flag before script guards, so that name is intentionally not used.

After a DSH owner-session/launch-record change, only these new services may need reconnection:

```sh
systemctl --user restart dsh-mcp-gateway.service
systemctl --user start dsh-mcp-tunnel.service
```

`BindsTo` stops the tunnel when its gateway stops; automatic restart of both after every dependency failure is not claimed. Both are enabled for the user manager's normal startup. The machine, user services and DSH must remain online. Preserve the private ledger across restarts; uncertain admissions must not be replayed under new keys.

## Deployment issues found and fixed

- Rootless systemd filesystem namespaces remapped host root-owned ancestors to UID65534. Strict ledger checks correctly rejected them. The isolated Nix fix removes only those incompatible namespace directives; private-file ownership checks are unchanged. Actual transient-unit fail-first/pass-after tests verify ownership, SQLite writes,0600 creation and directory fsync. The units retain supported restrictions but are **not filesystem sandboxes**.
- Challenges on nonexistent OAuth metadata routes made tunnel discovery infer broken OAuth. The gateway now returns404 for absent routes, after Host/Origin checks. Every actual `/mcp` request still requires the gateway bearer before methods, body parsing or tool discovery. No OAuth server is fabricated.
- Offline production deployment initially lacked locked registry metadata for a supply-chain check. A checked metadata fetch repaired that cache; the exact release then deployed offline with the policy enabled. No `trust-lockfile` bypass or lifecycle scripts were used.
