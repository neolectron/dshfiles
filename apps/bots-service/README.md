# Bots service

A normal Node.js HTTP app for provider-neutral Bots, with one engine, one durable store and provider adapters. It does not launch DSH, require a desktop helper, or create a replacement bot.

**Default: no adapters.** Explicit opt-in registers the existing Dot factory through its public Node modules. Choose either private DSH account authority or the legacy private read-only reference file. Registration exposes provider metadata, not a sample bot or authenticated account. Real account authentication and live DSH activation remain unverified; the successful Yield UI exchange is not a backend test.

The definitive product is intended to reuse the user's selected existing OpenAI login from DSH, **not require a browser-token handoff or an operator file of OpenAI credentials**. This app can now consume the public private-account-authority client and pass its access-only capability into Dot. The authority service key is a distinct backend credential, never an OpenAI token. Dot's account mode accepts only an explicit account ID; it has no credential-management grant, cookie, refresh-token read or cross-account fallback. Real selected-login Dot authorization and live deployment remain unproven. Renewed diagnosis identified the403 as an explicit Cloudflare browser challenge, not a proven OAuth rejection. Optional ordinary-browser transport now supports human admission entirely inside DSH, without stealth, challenge solving or importing an existing profile. Full synthetic GUI enrollment/connect/send/reply passes; it is not real-account acceptance.

## Build and run

Use official Node22.23.3 and the repository-pinned pnpm. Build the existing dshx/tooling prerequisites, then `@dshfiles/bots`, then this app; the root Turbo dependency graph can order those builds. From this app, `node --run build`, `node --run typecheck` and `node --run test` exercise the executable and real HTTP process lifecycle.

Run `node dist/main.js --help` for the fixed configuration contract:

- `BOTS_SERVICE_DATA_DIR`: explicit canonical absolute private directory, with an existing parent. A new/empty directory may become the dedicated service store; an unrelated nonempty directory is refused. Do not point this at a DSH home or an existing DSH store.
- `BOTS_SERVICE_TOKEN_FILE`: absolute path to a regular non-symlink service-token file owned by the service user with no group/other permissions. Supply a random32–512 character printable ASCII token, optionally followed by one newline. The value never belongs in argv, URLs or frontend code. This is a service credential, not a ChatGPT token.
- `BOTS_SERVICE_HOST`: defaults to `127.0.0.1`; `0.0.0.0` is an explicit container option.
- `BOTS_SERVICE_PORT`: defaults to8787; use0 for an ephemeral test listener.
- `BOTS_SERVICE_ADAPTERS`: empty by default, or explicit `openai-dot`. Unknown or duplicate names are refused. Concrete factories live only at this app's composition root, not in the neutral engine or UI.
- `BOTS_SERVICE_DOT_AUTHORITY_ORIGIN` and `BOTS_SERVICE_DOT_AUTHORITY_TOKEN_FILE`: both required for private DSH account authority, with explicit `BOTS_SERVICE_ADAPTERS=openai-dot`. Cannot be combined with `BOTS_SERVICE_CREDENTIALS_FILE`. The public Dot factory validates the origin before credential reads or store/engine creation: only a root HTTPS origin, or HTTP with literal `127.0.0.1`/`[::1]`, is admitted; no credentials, query, fragment or non-root path. Plain LAN HTTP and DNS `localhost` are refused. Use the public factory's policy rather than a separate app allowlist.
- The authority token file is an absolute private regular non-symlink file owned by the service user, bounded like the control-token file. Its contents must pass the public authority bearer schema and **must differ from `BOTS_SERVICE_TOKEN_FILE`**, including after rotation. Supply only the purpose-bound authority service key, not OpenAI credentials. Startup validates it locally without contacting the authority. Each account-access request rereads the private file, checks cancellation and validates the key again; replacing it with an invalid or control-service key fails closed. Nothing writes or serializes this key into Bot state, API output or logs. Do not mount a DSH home, cookies or refresh-token storage into this app.
- Optional managed-browser transport requires **all three** `BOTS_SERVICE_DOT_BROWSER_EXECUTABLE` (trusted absolute Chromium executable), `BOTS_SERVICE_DOT_BROWSER_PROFILE_PARENT` (existing canonical owner-only private directory, not a personal profile or the Bots data root), and `BOTS_SERVICE_DOT_BROWSER_ACCOUNT_ID` (one explicitly selected DSH account). It requires authority mode; partial/mixed configuration is refused. Each human start creates a fresh private profile; no provider request starts just because the service boots. The same browser is retained after explicit human completion, then the normal Dot adapter performs discovery and messaging. No credential-source fallback or web-session-token extraction is added. Default remains ordinary HTTP.
- `BOTS_SERVICE_CREDENTIALS_FILE`: required for legacy provider mode when private account authority is not configured. An explicit canonical absolute private regular file, owner-only permissions, no symlinks/hardlinks. It maps canonical `secret:ALIAS` or non-default-environment references to string values. Default `prod` keys omit `@prod`. The file is capped at256KiB,64 references,128KiB per scalar; invalid content yields fixed diagnostics without data/path echo. It is **plaintext private operator storage, not an encrypted vault or web-based onboarding**. Never put it in a build context/image or a browser field.

The app prints only a fixed readiness receipt with its non-secret listening origin and selected adapter IDs (or `none-configured`). The legacy reference backend loads one immutable whole-map process snapshot before engine startup and rejects detected edits during reading; atomically replace the file and restart the service to load another generation. It never watches files, scans HOME, imports DSH aliases or provides credential-write authority. Dot's optional vault-management capability is absent in both app modes; explicit grant attempts are refused. Legacy renewal may still occur in session memory, but nothing writes the reference file; account mode requests current access from its authority instead. SIGINT/SIGTERM stop HTTP/engine admission, close the human attempt and owned browser, then flush/close the domain and release its exclusive owner lease before closing the authority client and unregistering adapters. The neutral Node runtime's optional `beforeStorageRelease` composition hook retains exclusivity until resource cleanup is confirmed; failed cleanup retains the lease. Signals during startup cancel further authority reads, close opened file descriptors and prevent readiness reporting. Another process cannot open the same root. A crash, replaced lease or unconfirmed cleanup retains the lease: never auto-steal it or delete storage to force startup. Operator reconciliation is required after such a failure. Private POSIX local storage is supported; this is not distributed filesystem fencing.

The Bots control HTTP endpoint uses its own bearer service credential, strict existing Bots schemas and bounded bodies/deadlines. This token grants owner-level authority and is not the private account-authority key. Browser Origin headers and query credentials are rejected; DSH must call it through its Host. A trusted TLS reverse proxy is required for wider exposure. Plain LAN HTTP is not a proven safe account-authority deployment. Docker loopback addresses refer to the container itself; Host authority reachability, TLS/proxy termination and origin pinning must be reviewed together. The synthetic loopback tests do not prove that deployment topology. Do not publish this unaudited service directly to the Internet.

## Human enrollment inside DSH

Browser mode mounts six exact provider-owned private endpoints through the normal server's `privateEndpoints` extension seam. They inherit control-service authentication, bounded JSON/raster responses, no ambient browser authority/CORS, redacted failures and cancellation; there is no provider branch in the engine and no second outbox. The DSH Dot Host exposes them only through native BrowserPeer/Host/Origin/controller-capability admission—not generic RPC or agent tools. Humans use the new **Dot connection** page, then return to **Bots**. Closing that viewer after successful completion does not close the retained backend browser.

The Host may use `authorityTransport: loopback` for a separate owned127.0.0.1 account listener without rebinding/restarting its main GUI. It does not weaken native TLS/socket checks or trust forwarded headers. Native human sign-in access requires HTTPS or loopback HTTP. Existing-LAN-HTTP deployments can use their already-authorized local GUI origin; remote human sign-in needs TLS. See the [provider setup](../../plugins/@dshfiles/bot-openai-dot/README.md#managed-browser-admission-inside-dsh).

The full synthetic real-DSH journey passed twice: consent/raster/input, explicit completion, retained real Chromium with its own HttpOnly cookie, actual Dot decoder and one send/reply through the sole Node outbox, no Host data domain, then positive resource/process/lease cleanup. Real provider admission and the selected login's Dot grant are still unverified. Browser transport enforces real Chromium renderer sandboxing, bounded concurrent calls and first-party document policy; it is not a claim of OS-level provider-only egress confinement. External identity-provider SSO is outside its fixed first-party navigation policy. The existing Docker image/smoke is **HTTP-only**; deploying browser mode additionally requires a provisioned Chromium and verified sandbox-capable container runtime.

## Docker packaging

The Dockerfile consumes a **reviewed production-only pnpm deploy artifact for this app**, never a repository root, HOME, browser profile, credential directory or live DSH tree. The checked-in base is the official Node22.23.3 Linux-amd64 manifest pinned by digest. Images remain local unless publication is separately authorized.

Use a clean, independently owned source snapshot and private dependency installation, then deploy `@dshfiles/bots-service` into a disjoint temporary app directory. Do not run the pinned pnpm's legacy production deploy from a shared checkout: its saved workspace-state side effect can cause a later exec to prune development tools. The explicit proof helper below isolates that operation and verifies shared install metadata unchanged. Check source/build hashes, that dependency links resolve entirely inside the artifact, and that no private state was included. Build only that reviewed artifact directory. Supply the token as a read-only private file and the dedicated data root as a durable volume. Never mount the Docker socket, existing browser profile or DSH home. Restrict port publishing to the intended local interface. A network-disabled, non-root, read-only-rootfs synthetic smoke is sufficient for packaging checks; it is not provider authentication.

The fork's lock currently forces Cordis4.0.4 while the installed storage packages declare `~4.0.5`. Local runtime/API tests pass with the locked identity, but this range mismatch must remain visible; it is not a newly certified upstream compatibility claim. Do not upgrade the live Host or rewrite global overrides to hide it as part of packaging.

## Verified boundaries

Tests use only synthetic values and private temporary directories under the existing network guard. They cover normal Node readiness/HTTP authentication, revision persistence across process restart, SIGTERM lease release, refusal of missing/public/symlink token files, redacted failures and cleanup. Account-authority CLI tests use only a fake literal-loopback HTTP authority returning denial: account-ID metadata, absent credential management, fresh private-key reads/rotation, no key in state/output, and rejection of mixed/partial/unselected modes, unsafe origins, unsafe key files or reused control keys before creating the data root. No test connects to a real account, provider, DSH profile or current GUI. The reusable Bots runtime tests additionally verify real JSON send tombstones/retry, owner exclusivity, malformed-state preservation and replaced-lease refusal.

The DSH Host has an explicit profile-owned service placement mode with a per-request service-credential reference. It opens no local Bots domain/workers, never falls back to local on network failure, and does not stop this app on Host disposal. The Host still needs its existing storageDomain service activated, although it does not use that service for Bots data in service mode. This is not a live settings toggle or automatic migration.

In legacy mode, provider references resolve at this app's worker and Dot still requires **both access and session references**. DSH vault aliases/values are not automatically copied, and a fake second credential must not simulate account mode. Private authority mode instead uses the public access-only account capability and the selected account ID; the app never imports the AI Accounts runtime or reads its home/login storage. Neither backend service key is a ChatGPT credential.

An explicit optional `scripts/bots-service-container-proof.mjs --openssl=/absolute/openssl --nativeRuntime=/absolute/installed-runtime --pnpm=/absolute/pinned-pnpm` helper (repository root) now verifies the fresh production app with the actual installed native TLS WebServer and a host-network container. It fails closed on dirty production inputs, builds/deploys only in an owned archived-HEAD workspace with private dependency links and checks the shared checkout's install metadata unchanged. Root-cwd legacy production deploy is not safe with the pinned pnpm: it can poison saved workspace install state, allowing a later exec to prune dev tools. No shared metadata is blindly restored. The helper uses a private test CA and synthetic purpose keys only, normal Node TLS verification, non-root/read-only/cap-drop settings and exact-fixture fetch guards. Untrusted CA fails before authority reads; trusted CA delivers deliberately malformed synthetic access that is rejected before provider I/O; restart/lease release/redaction/owned cleanup pass. This is a test seam, not an OS firewall. It does not modify or certify the current plain-LAN-HTTP GUI, a bridge-network topology or whole-Host Cordis identity.

The real scratch GUI additionally verifies remote account-ID metadata and sanitized authority rejection, with no local Host Bots data or private browser values. This is a refusal fixture, not successful linking.

Not verified: real selected-account Dot authorization/session, backend renewal, successful GUI linking, secure current deployment or activation. This opt-in app wiring is not a completed end-to-end feature. No real message may be sent using the already-consumed Yield UI test authorization.
